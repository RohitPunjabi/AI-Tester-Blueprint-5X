01 · Purpose

Objective

Verify that the VWO login experience provides secure, reliable, accessible, and responsive entry to the VWO platform. Testing will cover authentication, validation, session behavior, account recovery, new-user registration navigation, visual themes, integrations, security, performance, and supported browser/device combinations described in the PRD.

95%+PRD login success-rate target; validate measurement definition and eligible-attempt denominator.
< 2 secondsPRD login-page load target on a standard connection; agree measurement method and percentile.
99.9%PRD high-availability objective; assess through service monitoring/SLO evidence, not a short UI run.
WCAG 2.1 AAAccessibility conformance target stated in the PRD.

02 · Coverage

Scope and Inclusions

In scope

  • Login page rendering, VWO branding, announcement banner, light/dark theme options, responsive layout, and links to free-trial registration and support.
  • Email/password authentication: valid and invalid credentials, required fields, email formatting, password feedback/requirements, field-level validation on blur, submission, loading state, and actionable errors.
  • Remember-me behavior, secure session creation, timeout/expiry, logout or session invalidation where accessible from the login journey, and redirect to the authenticated VWO dashboard.
  • Password reset request and completion, token validity/expiry, and recovery confirmation. Test only with controlled accounts and mailboxes.
  • Keyboard-only access, screen-reader semantics, labels, focus order/visibility, contrast, zoom/reflow, and touch target usability.
  • HTTPS and transport behavior, authentication/session protections, rate limiting, safe error responses, privacy/data handling, and security logging evidence.
  • Analytics events for login success/failure and integrations listed in the PRD, including SSO protocols and optional identity providers when enabled and supplied for the test environment.
  • Login-page load performance, authentication response behavior under agreed load, cross-browser compatibility, and regression coverage.

Out of scope

  • Functional testing of experimentation, personalization, analytics dashboards, and other post-login product modules except verifying successful handoff and destination.
  • Actual production penetration attacks, destructive load testing, or tests against real customer accounts/data.
  • Biometric authentication, adaptive authentication, and progressive web app behavior: listed as future enhancements, not committed release scope.
  • Unspecified product behavior, including exact password policy, timeout duration, lockout policy, supported browser versions, recovery channels beyond email, and numeric concurrency targets, until approved.
Scope confirmation required

The PRD mixes existing features, proposed requirements, optional integrations, and future enhancements. Product must identify which features are acceptance criteria for this release. Treat unsupported or unconfigured SSO/MFA/social-login paths as blocked or not applicable only after that decision is recorded.

04 · Triage

Defect Reporting Procedure

Log defects in the team-approved tracker (tool and project to be confirmed). Each report should include a concise title, environment/build, requirement or scenario ID, severity and priority, preconditions/test account type, exact reproduction steps, expected versus actual result, timestamp, browser/device, sanitized evidence, and relevant request/correlation ID. Never attach passwords, session cookies, reset links, or personal customer data.

SeverityGuidelineInitial response
Critical / BlockerAuthentication outage/bypass, credential or session exposure, broad account lockout, or release-critical flow unavailable.Immediate escalation; stop affected testing/release pending triage.
HighMajor login/recovery/SSO path fails for a material user group; serious accessibility or security control failure.Same-day triage; fix or explicit release decision required.
MediumFeature works with workaround or limited impact; non-critical validation or compatibility defect.Prioritize in triage and assign target sprint.
LowMinor visual/content issue with no meaningful task or compliance impact.Backlog with agreed owner and priority.

Workflow: New → Triaged → Assigned → In Progress → Fixed → Ready for Retest → Verified/Closed. Reopen if reproducible. QA lead publishes daily status during execution and escalates any P0/P1 security or release risk immediately. Owners and tracker are TBD.

05 · Approach

Test Strategy

  1. Requirement analysis and traceability: Review PRD, resolve ambiguities, map each accepted requirement to scenarios and evidence, and identify dependencies.
  2. Test design: Apply equivalence partitioning and boundary-value analysis to email/password/token inputs; decision tables to account state, remember-me, and MFA; state-transition testing to session and recovery token lifecycles; and use-case/error-guessing techniques to login and recovery paths.
  3. Build verification: Run smoke checks for availability, page rendering, core login, invalid credentials, recovery entry, and dashboard handoff. Stop deeper execution if a P0 smoke check fails.
  4. Functional and integration: Execute positive, negative, boundary, state, and end-to-end scenarios, including configured identity providers and event tracking.
  5. Non-functional: Conduct keyboard/screen-reader and WCAG checks; cross-browser/device coverage; approved security assessment; and measured performance/load tests with agreed thresholds.
  6. Regression and exploratory: Retest fixes, run prioritized regression each release, and explore interrupted networks, unusual input, rapid repeated submits, browser back/forward, and theme changes.
  7. Automation: Automate stable critical paths using Playwright with TypeScript where test infrastructure supports it. Keep secrets outside source control, isolate test data, and avoid assertions against unstable copy except where copy is a requirement.

Prioritization: P0 security and access-critical paths first, then P1 recovery, accessibility, configured integrations, and compatibility; P2 visual and lower-risk cases. Run smoke on every candidate build and full regression before release.

Metrics: Scenario pass/fail/blocked rate, defect count by severity, retest status, login success rate, page-load and authentication latency, error rate under load, accessibility findings, and test coverage against approved requirements. Business KPIs are monitored over a representative production period and are not inferred from a small QA sample.

06 · Timing

Test Schedule

Indicative two-sprint plan, consistent with the skill template. Dates and sprint length are not specified in the PRD and must be agreed with the delivery team.

Sprint 1 · Define and validate core

  • Confirm feature scope, environments, policies, test accounts, and acceptance thresholds.
  • Review requirements, risk, and traceability; prepare scenarios and data.
  • Run smoke and core email/password, validation, recovery, session, and dashboard handoff tests.
  • Start responsive, accessibility, and browser baseline checks; report defects and retest fixes.

Sprint 2 · Integrate and release

  • Test configured SSO/MFA/social integrations and analytics events.
  • Complete security, accessibility, cross-device, performance, and approved load testing.
  • Execute regression, fix verification, and pre-production smoke.
  • Publish test summary, residual risks, metrics, and release recommendation for approval.

08 · Readiness gates

Entry and Exit Criteria

Analysis and design

Entry: PRD and product owner available; QA owner assigned.

Exit: In-scope requirements identified, ambiguities/dependencies logged, coverage mapped, and test plan reviewed.

Test execution

Entry: Deployable build and QA URL available; smoke build stable; test accounts/data and integrations configured; test approval granted.

Exit: All planned P0 scenarios pass; all in-scope scenarios executed or explicitly dispositioned; no open Critical/High defect unless formally accepted; evidence and metrics recorded.

Release readiness

Entry: Candidate deployed to pre-production; release notes and known issues available; regression environment representative.

Exit: P0 smoke and agreed regression pass; security/accessibility/performance gates meet approved thresholds; residual risks and exceptions signed off.

Test closure

Entry: Execution complete or formally stopped; defects triaged; stakeholder decisions recorded.

Exit: Summary shared, test assets/evidence retained per policy, open defects assigned, and QA/release stakeholders approve closure.

Thresholds needing owner approval

Define acceptable authentication latency/error rate under load, concurrency profile, supported browser versions, password/session policies, accessibility exception policy, and the time window/measurement source for the 99.9% availability objective before these become pass/fail gates.

09 · Run protocol

Test Execution

  1. Confirm the build identifier, environment health, account readiness, change scope, and approvals.
  2. Run smoke tests. If a P0 fails, record the blocker, notify the owner, and pause dependent execution.
  3. Execute scenarios by priority and feature area; record actual results, evidence, timestamps, and defects as they occur.
  4. Run risk-approved non-functional tests only against the designated environment and agreed load/security limits.
  5. Retest fixes on the target build and run impacted regression; preserve traceability between defect and scenario.
  6. At cycle end, reconcile planned versus executed coverage, blockers, unresolved defects, and release risks with stakeholders.

10 · Completion

Test Closure

QA prepares a concise closure report with build/environment, scope changes, execution totals, requirement coverage, defect status by severity, outstanding risks and accepted exceptions, security/accessibility/performance observations, KPI measurement caveats, and a clear pass/conditional pass/fail recommendation. Product, engineering, security, and release owners review and record the go/no-go decision.

Tools
